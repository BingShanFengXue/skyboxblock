## 0. 一句话摘要

26.2 移植线把 1.21.1 的**抓帧 + 自研 shader**架构换成了**"每帧自绘一张天空 target + 方块面按屏幕投影采样"**，这是本轮所有差异的总根源：

1. 26.2 的 **Iris 适配层只剩 35 行**（1.21.1 是 261 行 + 3 个 `@Pseudo` Iris mixin），所以光影下**既读不到光影的天空，又在光影的 pass 图里多画了一遍原版天空** —— 这解释"有模组 + ITRP 世界天空全黑，而方块面反而正常"。
2. 26.2 的**环境状态（时间/雾/云参数/环境覆盖）在自绘路径里根本没接**：`SkyRendererHost` 一次都没读 `SkyboxConfig` / `SkyEnvironment`，26.2 的 `SkyDisplayState` 只存在于 `src/legacy-1.21.1`（不参与编译）。
3. 26.2 文档里的若干"✅ 已对齐"与归档截图**自相矛盾**（云、日月星、逐像素判据），需要按第 4 节的证据重定向。

## 3. 动态渲染已知问题的**真实成因**（按证据强度排序）

### 3.1 「有模组 + ITRP → 世界天空全黑，方块面反而正常」——最可能的机制

**证据链**

1. `SkyboxBlockClient.java:25-29`：自绘天空挂在 `START_MAIN`，**每帧在 `renderLevel` 之前**先调 `SkyRendererHost.tick()`。
2. `SkyRendererHost.java:156`：只有当 `rendererOwnsTarget == true`（26.2 的 3 参构造器）时才**不**设 `outputColorTextureOverride`；也就是说 26.2 路径**完全依赖 `SkyRenderer` 构造器里那张 target 自己生效**。
3. 同一次会话里，**同一个 target 的另一条通道（显式附件 RenderPass）能出像素**：
   `build/itrp-withmod-real.log:308` → `Missing program skyboxblock:clouds_cpu in override list…`，
   `:341` → `云层（CPU 求交）已绘制一帧 224x140`；
   `:381`/`:414` 同理 haze_blit。二者用的是 `createRenderPass(..., target.getColorTextureView(), ...)`（`SkyCloudCpu.java:112-118`、`SkyHazeBlit.java:80-86`）。
   ⇒ **target 本身没问题，问题在"构造器注入的输出"这条路在 Iris 下被改写。**
4. 后果正好对上现象：原版 sky disc 写进了 Iris 的 gbuffer（而不是我们的 target），把 `gbuffers_skybasic` 的填充**盖掉**：
   - ITRP 的 `gbuffers_skybasic` 是**标准天空色**（`shaders/program/gbuffers_skybasic.glsl`，`world1` 变体只 `#define GBUFFERS_SKYBASIC`），被盖掉后**没人补** → 天全黑；
   - Complementary 的天空色在 **composite 阶段由大气重新合成**（`lib/atmospherics/sky.glsl`、`lib/colors/skyColors.glsl`、`program/gbuffers_skytextured.glsl`），与 gbuffer 里被污染的值无关 → 天正常。
   这解释了两个包在同一机制下表现相反，**不需要**假设"ITRP 不支持 26.2"。

**(a) 自绘天空的输出目标在 Iris 下不可靠 → 污染 gbuffer；(b) 自建 pass 走 fallback（可能另有一层状态泄漏，未证实）。**

### 3.2 启动第一帧 `skyColor=#0`（文档把它当"模组自己画出黑天空"）

`SkyRendererHost.java:141-147`：`STATE.reset()` → `renderer.extractRenderState(level, partial, camera, STATE)` → `clear(target, STATE.skyColor)`。
日志 `build/client-262.log:305` 与 `build/itrp-withmod-real.log:307` 都是 `sky frame #1 … skyColor=#0`，`#2`/`#3` 才有值。
⇒ **第一帧 extract 没拿到环境（level/时间尚未就绪），clear 用 0 清屏**。只影响启动后一帧。
`SHADER-INCOMPAT-INVESTIGATION.md:219-222` 把它读成"我们自己的路径里天空全黑的可复现成因"，**归因过重**。

### 3.3 透视窗取样：矩阵来源与"翻 v"的自相矛盾（会直接影响光影下的对齐）

- 26.2 用 `camera.getViewRotationProjectionMatrix(VIEW_PROJECTION)`（`SkyRendererHost.java:143`）存进 `VIEW_PROJECTION`，但**方块面实际用的是 `viewRotationMatrix × projectionMatrix`**（`SkyBlockEntityRenderer.java:147`）；`SkyHost.viewProjection()` 的返回值**没有调用方**（`SkyHost.java:20-24` 注释仍说"用它取样"）。⇒ 存了一份、用了一份，注释与实现脱节。
- `SkyUvMath.project` 的 v 翻转：文件内**两段注释互相矛盾**——`:18` 说"v=0 在图像底部（GL 约定）"，`:30-31` 说"v=0 在**图像顶部**"，代码按后者（`0.5 - ndcY*0.5`）。
  `docs/TEST-BUILD.md:15-16` 又说"这一版修复了上下颠倒，回归已改成 v 越小越靠上"。**三处说法不可能同时为真**，且这是"整面上下颠倒"这类 bug 的唯一旋钮。
- 光影下正确做法应当是 Iris 自己的矩阵（1.21.1 就是这么干的：`CapturedRenderingState.getGbufferProjection()`，见 `legacy.../ModCompat.java:36-55`），而不是 `Camera` 的矩阵。`STATUS-26.2.md:543-556` 记录的"改用 `camera.getViewRotationProjectionMatrix` 更偏 90+"，真实原因是**当时自绘帧的行序与 UV 翻转不配套**，而不是"矩阵约定不同"。

### 3.5 自建 pass 可能真的在泄漏状态（未证实，但是最便宜的下一刀）

`docs/screenshots/conditions/itrp-window2.png`（窗口截图，同一次 ITRP 会话）里：
- 方块面底部出现**绿、粉、黑、白四个色块**（与 `docs/screenshots/styles/...`、`conditions/dh-on.png` 里的方块列一致 —— 那些正是**六列不同风格墙**的下半截）；
- 天空在地平线附近有一圈**异常绿光**。

合理解释：`START_MAIN` 里那两次 `createRenderPass(..., target.getColorTextureView(), Optional.empty())`（`SkyCloudCpu.java:112-118`）**换掉了当前绑定的 render pass / 视口 / 深度附件，却没有保存与恢复**；Iris 的 `CompositeRenderer`/vanilla 后续绘制于是用了错的 FBO 或错的 viewport，把别的 target 内容"漏"到画面里。

> 与 `docs/SHADER-INCOMPAT-INVESTIGATION.md:549-552` 的"下一步"一致：**`SKYBOX_CLOUDS=0 SKYBOX_HAZE_BLIT=0` 这一组对照至今没跑**。但注意 §2.2 的细节——关掉这两条**不会**改变 `SkyRenderer` 的调用（`SkyRendererHost.java:158-177` 与此无关），所以这组对照**只能回答 (b)，不能回答 (a)**。要回答 (a) 必须**单独**跳过 `renderer.*` 四个调用。

### 3.6 环境时间与光影合成（回答委托里的点名项）

- **环境时间**：26.2 自绘路径**完全没有**时间控制入口。相位、月相、日月角度全部来自 `SkyRenderState`（原版当帧），`SkyboxConfig.skyTime` / `SkyTimeClock` / `SkyEnvironment.sun_angle|moon_angle|star_angle` **不参与**。1.21.1 则全套在 `SkyDisplayState` 里（且 `SkyDisplayState` 现在只在 legacy）。
- **光影合成**：26.2 没有"合成后再修"的 hook。1.21.1 的 `resolveIrisView()`（`IrisPipelineMixin`，`finalizeLevelRendering` → `renderFinalPass` 之后）就是"等光影合成完，把天空窗口正确贴上去"这一步；26.2 把它换成了"合成前先自己画一张"。**两者不是"实现不同"，是"顺序不同"**——这是所有光影相关问题的根。

## 8. 给主线的可执行建议（按信息量/成本排序）

> 全部不涉及改主文件；建议 1 是**诊断实验**（B 甚至不用编译），做完就能把 §3.1/§3.5 的两种机制分开，再决定要不要动架构。

### 建议 1（最高性价比，30 分钟）：把 ITRP 全黑的成因**一刀切开**
两个独立实验各跑一次（都用 `tools/launch-262.py --world flat262` + `tools/capture-window.py` 抓窗口，不要用 `world-frame.png`）：

| 实验 | 做法 | 若"天空恢复" ⇒ | 若"仍黑" ⇒ |
|---|---|---|---|
| **A** | 只把 `SkyRendererHost.tick()` 里 `renderer.renderSkyDisc/renderSunriseAndSunset/renderSunMoonAndStars/renderDarkDisc` 四个调用短路（其余不动） | 责任 = **原版 SkyRenderer 在 Iris 下的输出目标**（§3.1，机制 a） | 责任 = 自建 pass / 状态泄漏（§3.5，机制 b） |
| **B** | `SKYBOX_CLOUDS=0 SKYBOX_HAZE_BLIT=0`（文档 549-552 行写了没做） | 责任 = 自建 `RenderPass` 状态泄漏（机制 b） | 机制 b 排除 |
